How grouping works

A group is a small heading and a count over a stack of rows, held together by whitespace. Selection is a raised plane, not a coloured bar. Only a window that actually floats gets a shadow; everything inside it separates by tone.

Semantic colour is separate

Green, amber and red mean running, waiting and failed. The user's accent is never one of them, so a red square still reads as failure when the accent is red.

One definition each

A state, a behaviour or a component that is drawn in two places will drift in one of them. Everything below is written down once and referenced everywhere else, so a row, a rule and a list entry cannot disagree about what selected looks like.

Five it closed

Selected and needs-attention were drawing the same amber wash, and a list entry drew selection a third way. Invalid had a light-theme frame that never got a dark counterpart. The focus ring existed in seven copies, one of them 4px. Two height classes were named for a size they did not set. A window was taking its shadow from the page.

Why orange moved

The warning bar and the cursor bar were both amber within one step of each other, so the two states were the same colour on a row. Warning is now orange and clears 4.6:1 as text, which leaves amber to mean two things: where you are, and what you chose.

What is deliberately not shared

App tile colours are data, not tokens, so they stay literal. A colour the user picked is drawn as itself. Both would be wrong to fold into the palette, because the palette is allowed to change underneath them.

Nothing new was drawn

Band, rail, group heading, row, search and hint bar are the components already in this deck. The only change is what the rail is a list of. A plugin that gains a setting tomorrow appears without a line of UI code, exactly as it does today.

Sections were already groups

The body has always stacked a plugin's groups in one scroll, so nothing has to move out of the way when the rail changes hands. The rail entries a plugin used to own become its group headings, which is where the deck already put them.

The filter is the only cross-plugin view

There is no filter field to find. Typing anything at all drops the rail and groups the hits by plugin, because a query like reconnect is the one time you want two plugins on screen at once. The hint bar is what says so, and escape puts the rail back.

Only plugins with a contract appear

Fifteen of the sixteen ship a qol-config.toml. removeapp has none, so it has no rail entry rather than an entry that opens an empty pane.

Motion budget

with_animation(..).repeat() repaints the whole window every vsync and has already cooked a laptop once in this workspace. The toast gets a one-shot slide and fade; the progress bar moves because its width changes, not because it animates.

Severity on the edge

A toast says what it is with a 4 px left bar, not a badge. Three toasts stacked read as a column of coloured bars before a single word is parsed.

The pad is the exception

It genuinely redraws at input rate, so it is the one surface where the paint cost is set by the hardware rather than by the user. Keeping it in a 452 px window rather than an 860 × 650 panel is what keeps that bounded.

One shell, five controllers

There is no drawing per device. Every profile paints the same unbranded body path and swaps four things over it: which of the two stick layouts to use, the four face marks and their colours, the names on the triggers and bumpers, and whatever sits in the middle. A device nobody has taught it about still gets a working diagram.

The only profile with symmetric sticks, which moves the d-pad up to the left shoulder and the shapes to the right.

Same shell and same offset layout as Xbox. Only the face letters swap sides and the centre cluster becomes minus, plus and home.

xboxXbox-style

View and menu are drawn as glyphs rather than words, because no unlicensed drawing can use the real marks.

genericGeneric raw controller

Anything the standard mapping does not claim lands in a discovered row under the pad, named by index, so an unknown device is still fully testable.

Why no branding

The face marks are drawn as letters and geometric shapes, and the centre buttons as glyphs. Nothing carries a logo, so the same drawing is legal to ship for a device the project has no relationship with, which is most of them.

Adding a sixth

A new profile is a layout choice, four face entries, two label pairs and a centre function. No new geometry, no new stylesheet, and it inherits every state the shared kit already draws.

The unknown device

When the standard mapping does not apply, the buttons are still enumerated and drawn in a row under the pad. The user sees b0 through b7 light up as they press, which is enough to map a pad by hand.
