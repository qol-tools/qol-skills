Bone and Amber · V2

Getting the code to match the spec

Five recon lanes read the tree. The gap is not what I assumed when I wrote the spec: the theme layer is large and already elaborate, the component kit it should hang from is dead code, and half the states the spec describes have never been drawn at all.

What the recon actually found

Each of these changes the plan. None of them were visible from the design side.

The thing that has to be decided first

The spec was written around a fixed amber. The product does not ship a fixed amber.

qol-theme ships six accent presets per mode with PROD_ACCENT_KEY = "amber" as the default, and two native theme keys already named bone and slate. So amber is the default accent, not a constant, and every accent-derived token in V2, the focused border, the halo, the amber wash, has to become a function of whatever the user picked. That is a different piece of engineering than writing a hex value into a table, and it decides the shape of phase one.

The plan

Six phases. The first one writes no pixels.

Phase 1Make the ladders testableno visual change

Right now a height change lands green and invisible. The settings-panel tests assert their own constants against their own formulas, so editing the constant edits the expectation too. The kit ladder is asserted by nothing at all.

  • Extend the existing gpui_surfaces_only_use_type_scale_sizes scan to heights, padding and radius, and stop excluding apps/qol-tray.
  • Assert every PANEL_* constant is a member of the V2 ladder, rather than equal to itself.
  • Add contrast-floor tests for the pairs the spec names: body 4.5:1, focus ring and state markers 3:1, in both themes.
Phase 2The palette layerneeds the accent decision

Add the roughly fourteen missing tokens. Most of them are alpha over a surface, and SystemPalette is solid u32 only, so this needs a real mechanism rather than fourteen more fields. Bless the generated web-UI CSS in the same commit.

Phase 3Give the states a home

Rebuild kit.rs as the component register the spec describes: a row-state type, a focus ring, one selected recipe. It is dead code today, which makes it cheap to change and the only honest place for "one definition per state" to live.

Phase 4Pilot on the settings panel

One renderer, one palette, and it exercises more V2 components than anything else: rows, rail, section labels, chips, fields, dropdown, colour wheel, gamepad. Every contract plugin inherits the result in one landing, which is what makes it the right pilot rather than the safe one.

Phase 5Draw the four missing statesnew plumbing

Attention, invalid and disabled are styling. Window-unfocused is not: no surface reacts to losing focus today, so it needs per-window focus tracking before it can swap a single token. This is the one phase that is not a restyle.

Phase 6Adoption, then the drawings

Launcher, alt-tab, cli-sessions, remove-app and qol-shot onto the kit rungs, then the two surfaces that need real drawing work rather than a token swap.

Three questions I should not answer alone

Is amber fixed, or is it whatever the user picked?

If the six accent presets stay, the spec's amber values become the default row of a table and the derived tokens become functions. If amber is now the product, the presets are dead and should be removed rather than quietly left in.

Blocks phase 2 entirely.
Do the laws apply to capture overlays?

The region selector is a fullscreen scrim over someone's actual screen, and the pinned preview floats over other windows. Neither is a pane, so "square windows, rounded controls" may simply not be about them.

Decides whether qol-shot is in scope or adjacent to it.
Does the web UI follow, or only drift?

It inherits palette values automatically through the generated CSS, but it has its own token layer, its own ladders and no V2 surface tokens. It can either be brought along deliberately or left to inherit colour and nothing else.

Doubles or halves the size of the whole job.
