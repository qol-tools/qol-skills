# qol-plugin-cli-sessions

CLI Sessions owns an always-on-top overview of live CLI sessions and the attention policy that decides which one needs the user. Terminal identity, discovery, screen reading, and focus are consumed from the shared terminal-sessions library; this plugin owns interpretation and presentation.

## Contract sources

- `plugin.toml` owns actions, exported launcher shortcuts, daemon metadata, declared capabilities, platform availability, and release artifacts.
- `qol-config.toml` owns settings sections, fields, and defaults.
- `qol-runtime.toml` owns the runnable action contract.
- `Cargo.toml` owns target-scoped dependencies.

## Source ownership

| Path | Responsibility |
|---|---|
| `src/cli.rs` | Headless command surface and doctor registration; `sessions` and `mcp` pass straight through to `libs/sessions-engine`. |
| `src/host/` | Terminal-host boundary (`TerminalHost`); the implemented host drives Kitty remote control. |
| `src/session/` | Session identity, registry, tool classification and completion policy, status, git context, and the target-selected service probe. |
| `src/attention/` | The pure attention reducer: `Evidence` in, `Phase` and next `Attention` out. |
| `src/signal/` | Screen and title evidence used to detect prompts and input requests. |
| `src/daemon/` | Reconcile loop that builds `Evidence` per pane and calls the reducer, action dispatch, and the knock courier (`knocks.rs`). |
| `src/storage/` | Session-state persistence, paths, and snapshots. |
| `src/config/` | Typed config loading. |
| `src/park/`, `src/parking.rs` | The `park` and `parking` commands that set a conversation aside and resume it, and `park --watch`, which closes a launched fork's tab once its turn ends. |
| `src/diagnostics/` | Anomaly detection and snapshot capture. |
| `src/ui/` | gpui overview panel: placement, rendering, navigation, selection, notification. |
| `src/doctor/` | Read-only checks with target-selected probes. |

## Interpretation strategy

Interpretation is split across two layers, and neither is a chain of conditionals. Per-tool reading lives in the shared terminal-sessions library: each harness implements `CliSessionStrategy` (`libs/terminal-sessions/src/cli/builtins/<tool>/`), registered by priority with a generic fallback, and its `describe` returns a `CliSessionDescriptor` carrying the display name and `CliSessionEvidence` (transcript runtime plus file activity). This plugin owns the attention policy: `daemon/reconcile.rs` combines that descriptor with screen evidence, screen movement, prompt state and the service probe into one `Evidence`, and `attention::reduce_with_policy` maps the previous `Attention` plus that evidence to the next status and a `Phase` (`Busy`, `Service`, `Blocked`, `Done`, `Idle`, `Hold`). The completion policy comes from `session/tool.rs`: harnesses with an explicit transcript terminal signal (claude, codex, pi) use `CompletionPolicy::Explicit`, everything else `Quiescent`. A session settles into "your turn" only after it stops moving for `GRACE_SECS` following a working episode, so a streaming session stays working and a first sighting never arms "your turn" from historical evidence; a `Historical` viewport holds the previous status instead of re-reading it. The generic strategy is busy-by-default because the absence of a foreground process is the idle signal. Adding support for a new CLI tool means adding a strategy in the library, registering it, and covering its evidence with cases - never branching on the tool inside shared code or the reducer.

The session's own transcript outranks the screen and the tab title. Each harness writes a JSONL transcript, and the type of its last complete entry is the deterministic runtime signal (the strategy's `tail_runtime`): a terminal entry reads Ready, a mid-turn entry reads Working, and a session whose transcript never resolves stays Unknown so the screen verdict still holds. Strong transcript Working beats a scrolled or historical screen. File freshness (`file_fresh`, `file_quiet_secs`) is supporting evidence only: it gates settling and suppresses a screen input request while the transcript is still being written, but freshness or growth alone never reads Busy. A turn in flight writes nothing for minutes at a time, with measured zero-write stretches of 260s inside a single live turn against a 120s freshness window, including one 4m36s pure-think gap, so a growth predicate reads a thinking session as idle. Screen movement stays a fallback for the generic strategy and for any harness with no transcript, never the primary reading for one that has it.

The terminal-entry sets live in each builtin's `metadata.rs` and are verified against real transcripts on disk rather than derived from documentation. codex ends a turn on `task_complete` or `turn_aborted`, read from `payload.type` when the entry's top-level `type` is `event_msg`; it flips to working within a second of submit because `task_started` is written at submit, so it has no fresh-session blind window. claude settles on a `system` entry with subtype `turn_duration`, a `user` interrupt note, or an `assistant` entry whose `message.stop_reason` is `end_turn`, `stop_sequence` or `max_tokens`; any other assistant, `user` or `attachment` entry reads Working, except three that leave the turn state as it was: a `hook_*` attachment (SessionStart, UserPromptSubmit and Stop hook output, which on disk is never directly followed by assistant output after a finished turn), a local slash command's `user` entries (`<local-command-caveat>`, `<command-name>`, `<local-command-stdout>`), and compaction output (the `isCompactSummary` user entry and the context attachments `file`, `compact_file_reference`, `invoked_skills`, `skill_listing`, `environment`, `model`, `output_style_instructions` and the `*_delta` listings); reading them as Working left a fresh session, one that ran `/reload-plugins`, or one Claude compacted while idle working forever, so knocks were never typed and park results were dropped. A real turn start after compaction still writes a user prompt or a `prompt_snapshot` attachment, which reads Working. A `<command-name>` first entry is always a local command; a prompt or skill command starts with `<command-message>` and reads Working. pi closes on a `message` entry whose `message.role` is `assistant` and whose `message.stopReason` is `stop`, `end_turn`, `length`, `error` or `aborted`; `toolUse` is the mid-turn stop reason and vastly outnumbers the real ones, so treating any `stopReason` as terminal reads every tool call as a finished turn. kimi has no transcript runtime yet: it reports `Unknown` and relies on file activity and the screen.

A transcript that reads Ready can still have work in flight. A claude turn that starts a background shell and then ends writes `end_turn`, and the shell's task notification starts the next turn when the job finishes. Claude Code publishes its live state as `status` in `<claude home>/sessions/<pid>.json`: `busy` mid-turn, `shell` at rest with a background shell running, `waiting` on a dialog, `idle` otherwise. Park closes a tab only while that reads `idle` (the strategy's `harness_busy`), because closing at `shell` kills the job; a live fork waiting on a background `sleep` read `shell` for the whole wait.

Ready and Done are the same live state on every harness, confirmed independently three times. A completed turn at rest is byte-identical to an idle one; the difference lives in history, not in the current reading. So anything that needs to fire once per completed turn triggers on the working-to-ready transition, never on the level.

An unsubmitted draft is never on disk. No harness persists one, confirmed by waiting on live sessions with typed input for 180s, 93s and 3.5 minutes. The only draft evidence is the live composer on screen (`composer_holds_draft` and `composer_draft` in the terminal-sessions library) plus a strategy's `draft_stash` key; never infer a draft from transcripts or file activity.

A park labels a session only at rest: `park_status` turns a settled status into Parked, but Working, Service and Needs you show through, because a session that parks with its terminal kept can be woken by a message or the user while its watcher still waits.

A parked conversation whose tab closed keeps a Parked row with no terminal behind it, so the user can find it and press Enter to reopen it: a park still waiting on its command whose runner lives, and a finished park whose runner closed the tab after its turn (`closed_at` on the record). Only the newest park of a conversation counts, and the row goes once any live session holds that conversation; the daemon then clears `closed_at`, so a reopened tab the user closes later is not parked again. Enter runs `park::open`, which reopens a finished park and resumes a waiting one in a new tab without stopping its command, so the result is still submitted when it exits; `unpark` instead stops the wait. The runner (`park --run`, and `park --watch`) registers its pid under the tray runtime directory's `detached/` through `qol_process::detached`, so the tray's orphan reaper, which kills every process running a binary from the plugins directory, leaves it alone across tray restarts and updates; before that, every tray update killed every PR watcher and no session heard of its failed checks. The record also keeps the command child's pid and identity, and the daemon relaunches a waiting or exited park whose runner and command are both gone, `RUNNER_RESTARTS` times at most, before it fails the park; a relaunched runner of an exited command only delivers the stored result. A wake counts as delivered once the conversation's own transcript holds that result's wake text, which carries the park id, and only after the runner recorded that it typed that wake (`wake_typed_at` on the park record, written once the text reached the terminal), so a turn from before the typing can never settle it. Each park is delivered on its own, so a result that finishes later cannot make an earlier one be typed again. A typed wake that the transcript never shows settles as delivered after ten seconds with its output named in the log instead of being typed again, so an unreadable transcript costs one typing and never a duplicate message or a failed park. Forks park only when asked (`session_fork` `park: true` or `qol sessions fork --park`), the switchboard's included.

Keep the reducer pure and total over previous attention and evidence - it is the part worth testing exhaustively, and it is where sticky states are honored: an acknowledged session stays acknowledged at the prompt, and a `NeedsYou` session with a live pending dialog holds instead of re-alerting on every poll.

## Switchboard and knocks

The switchboard is one Claude Code process, and a fork it starts for a project is a `project-fork` subagent inside that process, not a terminal of its own.
Forks run without worktree isolation.
Claude Code refuses to resume an isolated agent whose worktree is a repository's own checkout ("its worktree could not be verified (pin-is-own-launch-tree)", seen in 2.1.311 to 2.1.314), and isolation also holds every fork to its Bash guard for isolated agents, which refuses `$(...)`, computed operands and any unflattenable command whose text contains `git`.
Before qol-tools/qol#378, a WorktreeCreate hook pinned each fork to its project's main clone, so a fork that had ended a turn could never be answered again.
Instead, the switchboard writes the `qol-switchboard` plugin to the `plugin` folder in its own folder at every launch, rewriting only files that changed, and loads it with `--plugin-dir`.
The plugin's hooks module has one `agent.spawn` hook on `project-fork`: it starts a new fork in the folder named by the first line of its prompt, `Project: <path>`, refuses a prompt without that line, and passes a resume through, so a resumed fork keeps the cwd Claude Code recorded for it.
Agents a fork starts inherit its folder.
The plugin also keeps the fork board, so the switchboard model never relays a whole report (one night in October 2026 brought 58 reports, median 1.4k characters, and half of the switchboard's replies to them ran past 300 characters despite its one-line rule).
Its source is `libs/sessions-engine/src/switchboard/plugin/`: `register.tsx` (the hooks module), `types.d.ts` (its `$.state` contract, written as `types/index.d.ts`) and `register.test.tsx` (written as `tests/register.test.tsx`), embedded with `include_str!`.
A main-thread `session.append` hook catches each fork report in both shapes Claude Code delivers it, a `[Subagent hand-back]` agent message and a `<task-notification>` whose `<result>` holds the report, files the full text on the board and rewrites what the model reads to `[fork board] <key-name> · <kind> · <headline>`, plus a `Recommend:` line for an ask.
The fork prompt makes each report's first line `<kind>: <headline>` (ask, test, failed, blocked, waiting, merged or note); a report without it gets that line from `$.model.complete` on Haiku, and a note with its first line when Haiku fails.
The `board` pane groups forks into Needs you (ask, test, failed, blocked), Working (set at `agent.spawn` and at each fork `turn.start`), Waiting on a pull request and a folded Done group; a digit opens that fork's view (`$.ui.view`), `y` sends the top ask its recommended answer (`$.session.send`), and `$.ui.status` counts the forks that need the user.
It opens unasked from 144 columns and at any width with `/board`; the model reads the board with the `fork_board` tool (`mcp__qol-switchboard__fork_board`, in the lead's tools and `--allowedTools`).
Rows persist in `$.store` under `board:<session id>`, and keys of other conversations are deleted at start.
Check a change with `claude plugin validate <switchboard folder>/plugin` and `claude plugin test <switchboard folder>/plugin`; `claude -p --plugin-dir` with an `--agents` fork that prints a report shows what the lead reads.
The `pre-agent` PreToolUse hook refuses a fork call whose Project line is missing, relative, not an existing folder or not the folder's canonical spelling, since the fork's memory folder is keyed on the exact path, and a model the dispatch policy does not admit.
SubagentStart (`fork-context`) injects the project folder's instructions and memory.
A fork that starts in the switchboard's own folder, which means the plugin did not run, gets a notice instead: work in the folder on the task's first line, read its instructions and memory index, and end the report with `The qol-switchboard plugin did not run.`
On launch, with no switchboard live, the switchboard rewrites the meta of every fork an older version pinned, replacing `worktreePath`, `worktreeBranch` and `spawnedWithWorktree` with a `cwd`, so the fork resumes from the new process, and removes the retired `fork-pins` folder.
Rewriting a meta inside the process that spawned the fork does not help: that process keeps the isolation in memory and then refuses the resume as unrecorded.
A switchboard opened before the change still calls the retired `post-agent` and `worktree-create` hooks: the first exits quietly, and the second fails with a message to close the switchboard and open it again.
The switchboard resumes its last conversation started under its current role, matched by the `Switchboard role revision` line at the role's end, since a resumed conversation keeps the system prompt and agent listing it started with, and wakes the forks a restart stopped.
A fork is woken only when it was still in flight: its turn had not finished, or a background command of its own still ran when the switchboard stopped, and the user did not stop it.
`switchboard/background.rs` reads a background command as ended by its notice, either a `user` row whose `origin.kind` is `task-notification` or, for a command that ended while its fork was mid-turn, a `queued_command` attachment row with that origin, and by a TaskStop or KillShell call.
Background commands die with the switchboard process and leave no notice, so a command started before the stopped switchboard's own launch died at that earlier restart and does not count; `switchboard/resume.rs` reads the launch from the newest wake or handoff prompt the switchboard began with (a `user` row from the person whose text opens with "The switchboard restarted"), never a peer message or a quote.
Claude Code writes `stoppedByUser` into the meta of forks still waiting when it exits, so a fork's latest task notice in the switchboard's transcript decides first: `killed` is the user's stop.
Stopping an idle fork records no notice, only the flag, so the flag also counts when the meta was written more than 5 s after the fork's last transcript row and more than 5 s before the switchboard's transcript ended; a flag written as Claude Code exits does not.
The flag alone decides when a fork has no notice or the transcript cannot be read.
After a role change the new conversation's first prompt lists the last conversation's sleeping forks with their project, model, effort and transcript, and the switchboard starts each again as a new fork that reads that transcript.
A new or empty session is a fork too; only another tool or an ask for a terminal is forked into a terminal.
Park acts on the terminal and refuses the switchboard's, so a subagent fork cannot park; it runs the pull request watcher as a background Bash call instead, which `qol-workflow`'s `pr-watch-park-guard` enforces for any hook payload carrying `agent_id`.
The user talks to a subagent fork by selecting it in the agent list under the switchboard's prompt, and Esc there stops it.
The engine's `switchboard/rows.rs` writes each fork's row in that list: its key painted in a color picked by hashing the key (a fork that set its own color keeps the last one its transcript records), from a palette that leaves out yellow because Claude Code draws the model name in yellow; the fork's start date, always shown; and a row fitted to the terminal width so the date stays.
A fork that continues an earlier conversation quotes that conversation's last three exchanges at the start of its first reply, because the switchboard cannot show the earlier conversation in the fork's view.

The sessions engine (`libs/sessions-engine`) owns the switchboard, the mailbox, the board and the knock records; this plugin serves it as `sessions` and `mcp`, shows the switchboard as the master row, and delivers knocks. The daemon's courier types a pending knock only into a recipient that is one live session, settled (your turn, acknowledged or unknown, never parked) and showing an empty prompt, so it never interrupts a turn or a draft. It claims the knock under the per-recipient lock before typing and puts it back if typing fails, so a knock is neither lost nor typed twice. A knock whose recipient has no live terminal wakes it: the courier starts `qol-cli-sessions wake <key>` detached, once per knock text, and `park/wake.rs` resumes the newest park recorded for that key in a new tab with the knock as its first prompt. It wakes a finished, resumed or delivered park, or one still waiting on its command after its tab closed, whose runner then delivers the result into the reopened tab. It never wakes the switchboard, a conversation a live session already holds, or a park whose terminal is still open, and it puts the knock back when the resume fails. A key with no resumable park keeps its knock on disk until that key is live again. `session_send` still stores a message to a known key with no live terminal, and its result carries `live: false` so the sender, the switchboard first, tells the user the session was closed instead of reporting it sent, and the switchboard offers to continue it as a fork.

The daemon names tabs after their pull requests: each messaging tick, `daemon/tab_titles.rs` reads `qol_sessions_engine::pull_requests(key)` for every pane with a spawn key except the switchboard and, when the title it wants (`#237,#240 <key>`) differs from the one it last applied to that window, calls `TerminalSessionService::set_tab_title` (kitty: `@ set-tab-title --match window_id:<id>`). A tab name outranks the window title a harness keeps rewriting, so Claude Code's own titles cannot undo it, and a new window after unpark or reopen gets it on its first tick. The pull requests come from the engine's keyed record, which `session_send` text and the command of a `park` both feed (`park::record_pull_requests`), so the title never depends on an agent remembering to rename.

The daemon keeps the closed-session ledger the switchboard reads: `daemon/closed.rs` watches every described pane and, when a resumable conversation (an external id the tool can resume, never the switchboard) is missing from discovery for `MISSING_TICKS` ticks in a row or its tool exits, writes `sessions/closed/<external_id>.json` (`qol_terminal_sessions::closed::ClosedRecord`: tool, cwd, last title, spawn key, the permission mode, model, effort and Claude config dir that the strategy's `resume_settings` read while it was live, whether its role record says lane, and `closed_at`). Every open sighting is mirrored in `sessions/closed/live/`, so a conversation still open when the daemon stops is recorded at its last sighting once the restarted daemon misses it for `MISSING_TICKS` ticks. A conversation seen live again is forgotten, and only the daemon prunes records past `closed::RETENTION_SECS`, when it writes; readers never prune. The engine's `sessions_closed` lists the rest newest first, leaving out parked conversations, gone cwds and, unless asked, lanes; a row backed by a Claude Code conversation carries `transcript`, the path of its transcript, from which a switchboard fork continues it without a tab. `session_reopen` relaunches one through `qol_sessions_engine::resume::resume_launch`, which park resume also uses, and forgets its record only once the new tab reports the conversation.

The switchboard's sessions server gets the user's login-shell PATH (`$SHELL -l -i -c 'exec env'`), because the tray opens the switchboard with its own login-session PATH and every session forked from it inherits that server's PATH; without it, hooks that run `node` fail in every fork. `switchboard --here` runs claude as a child and removes the window's spawn tag when it exits, so the next chat in that window is not taken for the switchboard.

The switchboard runs in one Claude account, its `CLAUDE_CONFIG_DIR`. Opened from a terminal that sets one, it writes that path to `claude-config-dir` in its own folder, replacing an older record. A caller that sets none, such as the tray and the launcher (on macOS the tray is a launchd app with no account), reuses the recorded folder for the tab, its login and the lookup of the conversation to resume; only with no record, or a recorded folder that is gone, does it fall back to the current Claude home. Without the record a tray launch took the default home, whose `.claude.json` does not trust the switchboard folder, and claude refused to start. `switchboard --here` launches claude through the same account wrapper as a tab, so it starts logged in. The daemon logs a failed switchboard open at error, because the tray's stderr relay does not keep warnings; look for `switchboard:` in the tray log.

## Naming and per-tool backends (the law)

Every harness-specific behavior - naming, title grammars, metadata extraction, transcript location, screen classification, launch and resume arguments - is a method on the harness's `CliSessionStrategy` in `libs/terminal-sessions/src/cli/builtins/<tool>/`, never a `match` on the tool in shared code. Each strategy's `describe` resolves the display name in the same order: harness metadata name, then the harness's cleaned title, then `fallback_name` (spawn identity, then project directory). Presentation consumes the tool model (labels, accents, ids) instead of re-deriving strings, and the daemon, signal, and UI layers never branch on the tool; the one tool-keyed table in this plugin is the completion policy in `session/tool.rs`. Adding a harness means adding a strategy and registering it; the fallback chain stays untouched. The generic strategy has no title grammar, so an unrecognized harness degrades to the spawn key or project name instead of disappearing or misbranding. For the backend-split rule itself see `qol-arch-code`; this law's enforcement hook is described in the "Enforcement: tool-match guard" section of `qol-arch-code`.

## Common changes

**Support a new CLI tool:** add a `CliSessionStrategy` in the terminal-sessions library, register it, and choose its completion policy in `session/tool.rs`. Enrich display and runtime reading in the strategy; do not add tool branches to the registry, daemon, reducer, or UI.

**Add a terminal host:** implement the host boundary and its session binding. Discovery, screen reading, and focus belong to the shared terminal-sessions library - extend the library when the capability is host-neutral, and keep only host-specific wiring local.

**Change attention policy:** edit `attention::reduce_with_policy` and cover the change with `Evidence` cases rather than a live terminal.

**Change the panel:** keep the overview keyboard-first. It is an interactive gpui surface, so it must use `SurfaceKind::OverlayPanel` (normal, focusable, with the shared overlay state applied inside the reveal gate); non-focusable window kinds silently leak keystrokes to whatever is underneath, and a plain `SurfaceKind::Panel` drops the always-on-top behavior.

**Panel colours after focus leaves:** the panel goes quiet when it loses focus, except while a listed session's terminal holds keyboard focus. Discovery reports that as `SessionFacts::focused` (kitty: the focused OS window, its active tab, and that tab's active window; Windows: the session whose terminal window is the foreground window, and when several share it, the one titled like the selected tab), every reconcile tick records it with `Registry::observe_focus`, and `stays_live_while` reads `Registry::session_holds_focus`. Leaving the panel marks focus unread, which still holds, and reads it again 150 ms later; a discovery that started before the move cannot overwrite unread focus (`Registry::focus_read`), so jumping into a session never flashes grey. Leaving for another app greys the panel at the next read: 150 ms after leaving the panel, or the next reconcile tick (1 to 3 s) after leaving a session.

## Invariants

- Terminal identity, discovery, screen reading, and focus come from the shared library; this plugin does not re-implement them or poll independently when the library exposes a subscription.
- An unrecognized tool degrades to the generic strategy instead of disappearing from the overview.
- The attention reducer is pure and total over previous attention and evidence.
- Acknowledgement is sticky until the session genuinely changes phase.
- The panel is always-on-top, keyboard-navigable, and focusable.
- Doctor is read-only: it inspects host and storage metadata and queries inventory, and never creates state or launches a terminal.
- Voice owns recognition, routing, and conversation policy; neither plugin becomes the other's runtime broker.
