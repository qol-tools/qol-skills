# qol-plugin-cli-sessions

CLI Sessions owns an always-on-top overview of live CLI sessions and the attention policy that decides which one needs the user. Terminal identity, discovery, screen reading, and focus are consumed from the shared terminal-sessions library; this plugin owns interpretation and presentation.

## Contract sources

- `plugin.toml` owns actions, exported launcher shortcuts, daemon metadata, declared capabilities, platform availability, and release artifacts.
- `qol-config.toml` owns settings sections, fields, and defaults.
- `qol-runtime.toml` owns the runnable action contract.
- `Cargo.toml` owns target-scoped dependencies.

## Source ownership

| `src/config/` | Typed config loading. |
| `src/park/`, `src/parking.rs` | The `park` and `parking` commands that set a conversation aside and resume it, and `park --watch`, which closes a launched fork's tab once its turn ends. |

| `src/ui/` | gpui overview panel: placement, rendering, navigation, selection, notification. |
| `src/doctor/` | Read-only checks with target-selected probes. |

## Interpretation strategy

Interpretation is split across two layers, and neither is a chain of conditionals. Per-tool reading lives in the shared terminal-sessions library: each harness implements `CliSessionStrategy` (`libs/terminal-sessions/src/cli/builtins/<tool>/`), registered by priority with a generic fallback, and its `describe` returns a `CliSessionDescriptor` carrying the display name and `CliSessionEvidence` (transcript runtime plus file activity). This plugin owns the attention policy: `daemon/reconcile.rs` combines that descriptor with screen evidence, screen movement, prompt state and the service probe into one `Evidence`, and `attention::reduce_with_policy` maps the previous `Attention` plus that evidence to the next status and a `Phase` (`Busy`, `Service`, `Blocked`, `Done`, `Idle`, `Hold`). The completion policy comes from `session/tool.rs`: harnesses with an explicit transcript terminal signal (claude, codex, pi) use `CompletionPolicy::Explicit`, everything else `Quiescent`. A session settles into "your turn" only after it stops moving for `GRACE_SECS` following a working episode, so a streaming session stays working and a first sighting never arms "your turn" from historical evidence; a `Historical` viewport holds the previous status instead of re-reading it. The generic strategy is busy-by-default because the absence of a foreground process is the idle signal. Adding support for a new CLI tool means adding a strategy in the library, registering it, and covering its evidence with cases - never branching on the tool inside shared code or the reducer.

The session's own transcript outranks the screen and the tab title. Each harness writes a JSONL transcript, and the type of its last complete entry is the deterministic runtime signal (the strategy's `tail_runtime`): a terminal entry reads Ready, a mid-turn entry reads Working, and a session whose transcript never resolves stays Unknown so the screen verdict still holds. Strong transcript Working beats a scrolled or historical screen. File freshness (`file_fresh`, `file_quiet_secs`) is supporting evidence only: it gates settling and suppresses a screen input request while the transcript is still being written, but freshness or growth alone never reads Busy. A turn in flight writes nothing for minutes at a time, with measured zero-write stretches of 260s inside a single live turn against a 120s freshness window, including one 4m36s pure-think gap, so a growth predicate reads a thinking session as idle. Screen movement stays a fallback for the generic strategy and for any harness with no transcript, never the primary reading for one that has it.

The terminal-entry sets live in each builtin's `metadata.rs` and are verified against real transcripts on disk rather than derived from documentation. codex ends a turn on `task_complete` or `turn_aborted`, read from `payload.type` when the entry's top-level `type` is `event_msg`; it flips to working within a second of submit because `task_started` is written at submit, so it has no fresh-session blind window. claude settles on a `system` entry with subtype `turn_duration`, a `user` interrupt note, or an `assistant` entry whose `message.stop_reason` is `end_turn`, `stop_sequence` or `max_tokens`; any other assistant, `user` or `attachment` entry reads Working, except two that leave the turn state as it was: a `hook_*` attachment (SessionStart, UserPromptSubmit and Stop hook output, which on disk is never directly followed by assistant output after a finished turn) and a local slash command's `user` entries (`<local-command-caveat>`, `<command-name>`, `<local-command-stdout>`); reading them as Working left a fresh session, or one that ran `/reload-plugins`, working forever. A `<command-name>` first entry is always a local command; a prompt or skill command starts with `<command-message>` and reads Working. pi closes on a `message` entry whose `message.role` is `assistant` and whose `message.stopReason` is `stop`, `end_turn`, `length`, `error` or `aborted`; `toolUse` is the mid-turn stop reason and vastly outnumbers the real ones, so treating any `stopReason` as terminal reads every tool call as a finished turn. kimi has no transcript runtime yet: it reports `Unknown` and relies on file activity and the screen.

A transcript that reads Ready can still have work in flight. A claude turn that starts a background shell and then ends writes `end_turn`, and the shell's task notification starts the next turn when the job finishes. Claude Code publishes its live state as `status` in `<claude home>/sessions/<pid>.json`: `busy` mid-turn, `shell` at rest with a background shell running, `waiting` on a dialog, `idle` otherwise. Park closes a tab only while that reads `idle` (the strategy's `harness_busy`), because closing at `shell` kills the job; a live fork waiting on a background `sleep` read `shell` for the whole wait.

Ready and Done are the same live state on every harness, confirmed independently three times. A completed turn at rest is byte-identical to an idle one; the difference lives in history, not in the current reading. So anything that needs to fire once per completed turn triggers on the working-to-ready transition, never on the level.

An unsubmitted draft is never on disk. No harness persists one, confirmed by waiting on live sessions with typed input for 180s, 93s and 3.5 minutes. The only draft evidence is the live composer on screen (`composer_holds_draft` and `composer_draft` in the terminal-sessions library) plus a strategy's `draft_stash` key; never infer a draft from transcripts or file activity.

A park labels a session only at rest: `park_status` turns a settled status into Parked, but Working, Service and Needs you show through, because a session that parks with its terminal kept can be woken by a message or the user while its watcher still waits.

A parked conversation whose tab closed keeps a Parked row with no terminal behind it, so the user can find it and press Enter to reopen it: a park still waiting on its command whose runner lives, and a finished park whose runner closed the tab after its turn (`closed_at` on the record). Only the newest park of a conversation counts, and the row goes once any live session holds that conversation; the daemon then clears `closed_at`, so a reopened tab the user closes later is not parked again. Enter runs `park::open`, which reopens a finished park and resumes a waiting one in a new tab without stopping its command, so the result is still submitted when it exits; `unpark` instead stops the wait. The runner (`park --run`, and `park --watch`) registers its pid under the tray runtime directory's `detached/` through `qol_process::detached`, so the tray's orphan reaper, which kills every process running a binary from the plugins directory, leaves it alone across tray restarts and updates; before that, every tray update killed every PR watcher and no session heard of its failed checks. The record also keeps the command child's pid and identity, and the daemon relaunches a waiting or exited park whose runner and command are both gone, `RUNNER_RESTARTS` times at most, before it fails the park; a relaunched runner of an exited command only delivers the stored result. The wake is typed into the conversation at most twice: a runner that types it and cannot confirm the submit types it once more, and when that second typing still does not confirm, the park settles as delivered instead of typing the same text again, because every retype lands in the chat as another copy of the same message. Forks park only when asked (`session_fork` `park: true` or `qol sessions fork --park`), the switchboard's included.

Keep the reducer pure and total over previous attention and evidence - it is the part worth testing exhaustively, and it is where sticky states are honored: an acknowledged session stays acknowledged at the prompt, and a `NeedsYou` session with a live pending dialog holds instead of re-alerting on every poll.

## Switchboard and knocks

The sessions engine (`libs/sessions-engine`) owns the switchboard, the mailbox, the board and the knock records; this plugin serves it as `sessions` and `mcp`, shows the switchboard as the master row, and delivers knocks. The daemon's courier types a pending knock only into a recipient that is one live session, settled (your turn, acknowledged or unknown, never parked) and showing an empty prompt, so it never interrupts a turn or a draft. It claims the knock under the per-recipient lock before typing and puts it back if typing fails, so a knock is neither lost nor typed twice. A knock whose recipient has no live terminal wakes it: the courier starts `qol-cli-sessions wake <key>` detached, once per knock text, and `park/wake.rs` resumes the newest park recorded for that key in a new tab with the knock as its first prompt. It wakes a finished, resumed or delivered park, or one still waiting on its command after its tab closed, whose runner then delivers the result into the reopened tab. It never wakes the switchboard, a conversation a live session already holds, or a park whose terminal is still open, and it puts the knock back when the resume fails. A key with no resumable park keeps its knock on disk until that key is live again. `session_send` still stores a message to a known key with no live terminal, and its result carries `live: false` so the sender, the switchboard first, tells the user the session was closed instead of reporting it sent, and the switchboard offers to reopen it with `session_reopen`.

The daemon names tabs after their pull requests: each messaging tick, `daemon/tab_titles.rs` reads `qol_sessions_engine::pull_requests(key)` for every pane with a spawn key except the switchboard and, when the title it wants (`#237,#240 <key>`) differs from the one it last applied to that window, calls `TerminalSessionService::set_tab_title` (kitty: `@ set-tab-title --match window_id:<id>`). A tab name outranks the window title a harness keeps rewriting, so Claude Code's own titles cannot undo it, and a new window after unpark or reopen gets it on its first tick. The pull requests come from the engine's keyed record, which `session_send` text and the command of a `park` both feed (`park::record_pull_requests`), so the title never depends on an agent remembering to rename.

The daemon keeps the closed-session ledger the switchboard reads: `daemon/closed.rs` watches every described pane and, when a resumable conversation (an external id the tool can resume, never the switchboard) is missing from discovery for `MISSING_TICKS` ticks in a row or its tool exits, writes `sessions/closed/<external_id>.json` (`qol_terminal_sessions::closed::ClosedRecord`: tool, cwd, last title, spawn key, the permission mode, model, effort and Claude config dir that the strategy's `resume_settings` read while it was live, whether its role record says lane, and `closed_at`). Every open sighting is mirrored in `sessions/closed/live/`, so a conversation still open when the daemon stops is recorded at its last sighting once the restarted daemon misses it for `MISSING_TICKS` ticks. A conversation seen live again is forgotten, and only the daemon prunes records past `closed::RETENTION_SECS`, when it writes; readers never prune. The engine's `sessions_closed` lists the rest newest first, leaving out parked conversations, gone cwds and, unless asked, lanes, and `session_reopen` relaunches one through `qol_sessions_engine::resume::resume_launch`, which park resume also uses, and forgets its record only once the new tab reports the conversation.

The switchboard's sessions server gets the user's login-shell PATH (`$SHELL -l -i -c 'exec env'`), because the tray opens the switchboard with its own login-session PATH and every session forked from it inherits that server's PATH; without it, hooks that run `node` fail in every fork. `switchboard --here` runs claude as a child and removes the window's spawn tag when it exits, so the next chat in that window is not taken for the switchboard.

## Naming and per-tool backends (the law)

Every harness-specific behavior - naming, title grammars, metadata extraction, transcript location, screen classification, launch and resume arguments - is a method on the harness's `CliSessionStrategy` in `libs/terminal-sessions/src/cli/builtins/<tool>/`, never a `match` on the tool in shared code. Each strategy's `describe` resolves the display name in the same order: harness metadata name, then the harness's cleaned title, then `fallback_name` (spawn identity, then project directory). Presentation consumes the tool model (labels, accents, ids) instead of re-deriving strings, and the daemon, signal, and UI layers never branch on the tool; the one tool-keyed table in this plugin is the completion policy in `session/tool.rs`. Adding a harness means adding a strategy and registering it; the fallback chain stays untouched. The generic strategy has no title grammar, so an unrecognized harness degrades to the spawn key or project name instead of disappearing or misbranding. For the backend-split rule itself see `qol-arch-code`; this law's enforcement hook is `qol-workflow:deny-tool-matches`.

## Common changes

**Support a new CLI tool:** add a `CliSessionStrategy` in the terminal-sessions library, register it, and choose its completion policy in `session/tool.rs`. Enrich display and runtime reading in the strategy; do not add tool branches to the registry, daemon, reducer, or UI.

**Add a terminal host:** implement the host boundary and its session binding. Discovery, screen reading, and focus belong to the shared terminal-sessions library - extend the library when the capability is host-neutral, and keep only host-specific wiring local.

**Change attention policy:** edit `attention::reduce_with_policy` and cover the change with `Evidence` cases rather than a live terminal.

**Change the panel:** keep the overview keyboard-first. It is an interactive gpui surface, so it must use `SurfaceKind::OverlayPanel` (normal, focusable, with the shared overlay state applied inside the reveal gate); non-focusable window kinds silently leak keystrokes to whatever is underneath, and a plain `SurfaceKind::Panel` drops the always-on-top behavior.

**Panel colours after focus leaves:** the panel goes quiet when it loses focus, except while a listed session's terminal holds keyboard focus. Discovery reports that as `SessionFacts::focused` (kitty: the focused OS window, its active tab, and that tab's active window; Windows: the session whose terminal window is the foreground window, and when several share it, the one titled like the selected tab), every reconcile tick records it with `Registry::observe_focus`, and `stays_live_while` reads `Registry::session_holds_focus`. Leaving the panel marks focus unread, which still holds, and reads it again 150 ms later; a discovery that started before the move cannot overwrite unread focus (`Registry::focus_read`), so jumping into a session never flashes grey. Leaving for another app greys the panel at the next read: 150 ms after leaving the panel, or the next reconcile tick (1 to 3 s) after leaving a session.

## Invariants

- Terminal identity, discovery, screen reading, and focus come from the shared library; this plugin does not re-implement them or poll independently when the library exposes a subscription.
- An unrecognized tool degrades to the generic strategy instead of disappearing from the overview.
- The attention reducer is pure and total over previous attention and evidence.
- Acknowledgement is sticky until the session genuinely changes phase.
- The panel is always-on-top, keyboard-navigable, and focusable.
- Doctor is read-only: it inspects host and storage metadata and queries inventory, and never creates state or launches a terminal.
- Voice owns recognition, routing, and conversation policy; neither plugin becomes the other's runtime broker.
